## Product truth

The repository implements a connected product suite, not a single-purpose CRM:

1. Australian Energy Assessments provides household electricity and gas comparison, NEM12 analysis, upgrade scenarios, planning, guides, rebates and assessment education.
2. TLink provides a privacy-protected household-to-trade marketplace.
3. TLink provides an installer and wholesaler operating platform covering customers, jobs, quotes, scheduling, field work, invoices, payments, assets, service and supply workflows.
4. AEA Field is a narrower native technician client with encrypted offline work and server-authoritative synchronisation.

This identity is explicit in `docs/RELEASE_TRUTH.md:9-14`. The active commercial decision is that verified trades receive core tools for A$0 and that the operating product acquires marketplace supply rather than selling subscriptions (`ROADMAP.md:177-195`; `src/app/direct-trade/membership/page.tsx:26-65`; `src/lib/direct-trade-entitlements.ts:120-143`). Existing Stripe subscribers retain a billing-portal transition path, but paid access to core functionality is deprecated (`docs/RELEASE_TRUTH.md:36-38`).

## Product-level findings

### PF-001: The product is broader than its release gate

- Category: commercial/product truth
- Severity/Priority: High/P0
- Status: `PARTIAL`
- Confidence: High
- Evidence: the current implementation spans the workflow, but the formal replacement-product gate still requires complete offline materials/forms/signature/invoice, supply reconciliation, provider sync, asset update and store distribution (`ROADMAP.md:735-751`).
- Intended/current behavior: the suite intends to be a complete free trade operating system; today it is a deep CRM/workflow platform with several end-to-end gaps and externally blocked integrations.
- Impact/root cause: marketing it as a complete incumbent replacement could impose migration and operational risk on trades. Product delivery has moved faster than gate reconciliation.
- Remediation/acceptance: market only evidenced slices. The full replacement claim is permitted only when every gate has a dated executable test and runtime proof, with rollback and export evidence.
- Release blocking: Yes for a broad “complete trade-management replacement” claim; no for bounded existing workflows.
- Owner confirmation: Product/commercial owner.

### PF-002: Provider adapters are deployed code, not operational integrations

- Severity/Priority: High/P0
- Status: `PARTIAL`

- Evidence: Sites v187 explicitly states central Google, Microsoft, Xero, MYOB, QuickBooks, Stripe and Square registrations/credentials were absent (`docs/RELEASE_TRUTH.md:118-119`); the current handover records mixed later authority gates (`docs/HANDOVER_NEXT_TASK.md:186`).
- Intended/current behavior: installers connect their own providers; current code correctly exposes unavailable/configuration states, but operational availability varies by provider.
- Impact/root cause: a UI or adapter presence can be mistaken for a usable integration. External registration, identity, billing and compliance decisions are not code tasks.
- Remediation/acceptance: one designated sandbox owner must complete and evidence OAuth, exact-scope export/payment, callback verification, idempotency, disconnect and recovery for each provider.

### PF-003: Owner data portability and recovery are not evidenced product capabilities

- Category: data integrity/recovery
- Severity/Priority: Critical/P0
- Status: `UNKNOWN`
- Confidence: Medium
- Evidence: the strategy says durable export and retention should be guarantees (`docs/COMPETITIVE_PRODUCT_STRATEGY.md:40,65-67`), while no tracked backup, restore, DR or owner export document was found by `git ls-files` pattern searches.

- Release blocking: Yes for sole-system-of-record or durability claims.

### PF-004: The released generic Database Console should be withdrawn

- Category: security/data integrity
- Severity/Priority: High/P0
- Status: `VERIFIED DEPLOYED`
- Confidence: High
- Evidence: `docs/RELEASE_TRUTH.md:124` records Sites v199 and signed-in non-mutating QA across 145 application tables. Source makes other syntactically valid application tables visible by default (`src/lib/admin-database-console.ts:131-151`; `test/admin-database-console.test.mjs:62-67`). Name-based redaction still leaves broad identity, contact, address, free-text, financial and operational data readable; the three generic mutations do not call the authoritative saved-view or schedule services (`docs/audit/2026-07-21-complete-current-state/13_DATABASE_CONSOLE_SECURITY_REVIEW.md:111-147`).
- Intended/current behavior: the deployed console provides deliberate owner inspection and bounded one-row repair without arbitrary SQL. The final security decision is that this generic browse/mutation design should not remain (`docs/audit/2026-07-21-complete-current-state/18_FINDINGS_RISKS_ASSUMPTIONS_AND_DECISIONS.md:114-123,340-344`).
- Impact/root cause: compromise of one high-value owner session can disclose cross-tenant data and future schema; generic mutation can drift from domain rules and side effects; audit records cannot restore deleted rows and independent recovery is unproven.
- Remediation/acceptance: withdraw the Database navigation and deny `/api/admin/database`; abandon generic row mutation. If an evidenced operational need remains, implement only explicitly classified, default-deny, projected read-only diagnostic views. Implement repairs as named domain commands such as `reset_owner_saved_view`, `repair_member_working_hours` or `remove_invalid_unavailability`, reusing authoritative services with purpose, approval, preview, alerting and proven recovery.
- Release blocking: Yes for retaining or expanding the generic console. Acceptance requires that no production caller can enumerate arbitrary application tables or execute generic insert/delete; security and data owners must authorise withdrawal/redesign and any temporary exposure.
- Owner confirmation: Business owner, data owner and security reviewer.

### PF-005: Conditional fixture skips weaken comparator parity certainty

- Category: calculation/test evidence
- Severity/Priority: Medium/P1
- Status: `PARTIAL`
- Confidence: High
- Evidence: `test/electricity-model.test.js:205` and `test/nem12-typed-parity.test.mjs:92` skip when a supplied Origin fixture is absent; the current v199 release record still reports exactly two intentional skips (`docs/RELEASE_TRUTH.md:124`).
- Intended/current behavior: typed and compatibility parsers should agree on supplied real-format evidence; current runs can omit that evidence.
- Impact/root cause: a release can pass without the most direct compatibility fixture.
- Remediation/acceptance: define a privacy-safe fixture provenance and require it, or replace it with an equivalent committed synthetic fixture whose semantics are validated.
- Release blocking: Yes for legacy retirement; no for continued rollback availability.
- Owner confirmation: Comparator/calculation owner.

## Product audit conclusion

The suite contains unusually broad implemented workflow depth for its age and has strong privacy and authoritative-record design intent. The defensible current description is: an energy-comparison, protected marketplace and trade-operations platform recorded deployed through Sites v199, with a substantial web CRM, bounded customer links, native field foundations and multiple provider adapters, but with incomplete owner-controlled recovery, incomplete full offline job completion, uneven provider activation, stale commercial/product documents and no store-distributed native application. It should not yet be described as a fully proven replacement for an incumbent trade-management system.
